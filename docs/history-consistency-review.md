# 이력 데이터 일관성 보강 검토

검토일: 2026-10-07. 앞선 이력 책임 분리 패키지는 사용자가 정상 작동을 확인했다. 이번 단계는 실패 조건 재현과 정책 검토이며, 실행 코드와 배포 ZIP은 변경하지 않는다.

## 재현 결과

`tests/qgis_history_failure_audit.py`를 QGIS 3.44.14와 4.2.2의 Python에서 실행했다. 두 버전 모두 다음 결과가 나왔다.

| 작업 | 실패 조건 | 실제 데이터 | 현재 반환 또는 안내 |
| --- | --- | --- | --- |
| 새 이력 추가 | 안내 대상이 읽기 전용 | 경로 추가, 해당 안내 0건 | append가 True 반환 |
| 파일 불러오기 | 경로 대상이 읽기 전용 | 경로 추가 없음, 연결 경로 없는 안내 1건 추가 | 경로 1건·안내 1건 불러오기 완료 |
| 개별 삭제 | 경로 대상이 읽기 전용 | 경로 남음, 안내 삭제, 활성 이력 ID 해제 | 선택 이력 삭제 완료 |
| 전체 삭제 | 안내 대상이 읽기 전용 | 경로 삭제, 안내 남음 | 전체 이력 삭제 완료 |

읽기 전용 대상을 QGIS의 실제 `delimitedtext` provider로 만들고 `addFeature`와 `deleteFeatures`가 False를 반환하며 데이터가 유지되는 것을 먼저 확인했다. import 원본은 실제 GeoPackage이며 실제 QGIS 메모리 provider가 나머지 데이터를 추가·삭제했다. UI 파일 선택과 삭제 확인 응답만 mock했다. 모든 데이터와 파일은 임시 fixture다.

일반 플러그인은 정상 메모리 레이어를 생성하므로 이 실험은 일상 사용 중 오류가 발생했다는 증거가 아니다. 저장소의 provider가 실패했을 때 반환값 무시와 부분 적용이 실제 잘못된 상태를 만든다는 증거다. 쓰기 가능한 메모리 provider의 부분 성공·예외와 복구 실패까지 이 실험으로 확인한 것은 아니다.

스크립트의 성공 종료는 **현재 결함 재현에 성공**했다는 의미다. 정상 동작 테스트나 수정 완료 기준으로 쓰지 않는다. 구현 시 기대값을 실패 차단·복구 결과로 바꾼 회귀 검증을 별도로 만든다.

## 우선 적용할 정책

### 1. 실패를 완료로 표시하지 않기

provider의 단일·배치 추가, 삭제 반환값을 확인한다. 배치 추가는 QGIS Python의 `(성공 여부, feature 목록)` 반환 구조도 처리한다. 요청한 개수와 실제 반영 개수를 구분하고, 실패에서 준비한 개수를 완료 건수로 반환하지 않는다.

현재 `append`의 정상 완료 의미와 파일 가져오기의 `(경로 건수, 안내 건수)` 반환은 유지할 수 있다. 실패는 `RuntimeError` 계열의 명시적 이력 작업 오류로 전달하며 원인·작업 종류·복구 결과를 포함한다. 플러그인은 실패를 받아 로그와 오류 안내를 표시하고 완료 안내를 건너뛴다.

### 2. 변경 전 두 대상의 상태를 확인하기

변경할 feature와 ID를 먼저 준비하고, 경로·안내 양쪽 레이어의 유효성·provider·필요한 편집 capability를 확인한다. 예를 들어 안내 삭제도 필요한 작업이라면 경로를 지우기 전에 안내의 삭제 가능 여부도 확인한다. 데이터가 없어서 해당 작업이 필요 없는 레이어는 불필요한 capability를 요구하지 않는다.

이 확인으로 이번 읽기 전용 재현 조건은 데이터 변경 전에 거부할 수 있다. 다만 capability가 있다고 실제 쓰기가 반드시 성공하는 것은 아니므로 반환값 확인을 생략할 근거는 아니다.

### 3. 부분 반영을 복구하고 결과를 확인하기

정상 메모리 이력에 대한 첫 보강은 기존 레이어 객체를 유지하는 checked write와 보상 복구 방식을 권장한다. 작업 전 영향을 받는 feature·geometry·속성·선택과 실제 feature ID를 기록한다. 이후 단계가 실패하면 이번 작업에서 변경된 데이터를 되돌리고, 양쪽 데이터가 원래 상태로 돌아왔는지 확인한다.

- 추가: 기존 feature를 건드리지 않고 이번 작업으로 추가된 경로·안내를 제거한다. `addFeatures`가 False라도 일부 반영됐을 가능성을 고려해 실제 대상 ID 차이와 데이터를 확인한다.
- 삭제: 삭제 전 feature 복사본으로 제거된 데이터를 복원한다. 재추가 시 feature ID가 달라질 수 있으므로 원래 feature ID가 그대로 유지된다고 가정하지 않는다. history_id와 안내 sequence를 기준으로 UI 선택을 복원한다.
- 파일 가져오기: 경로와 안내를 먼저 모두 준비하고 저장소에 한 작업으로 전달한다. 경로 적용과 안내 적용을 서로 독립된 완료로 처리하지 않는다.

두 메모리 레이어는 하나의 DB 트랜잭션이 아니다. 보상 복구도 실패할 수 있으므로 **원자적 저장**이라고 표시하지 않는다. layer 편집 버퍼를 쓰더라도 두 레이어의 commit이 자동으로 하나의 트랜잭션이 된다고 가정하지 않는다.

복구에 실패하면 부분 변경이 남았다는 오류와 실제 경로·안내 상태를 보여준다. 다음 정상 작업처럼 그대로 진행하지 않고 해당 저장소의 추가 변경을 차단하는 복구 필요 상태를 검토한다. 오류 안내는 어떤 작업이 실패했고 데이터가 복원됐는지 또는 일부 남았는지 구체적으로 구분한다.

### 4. UI는 실제 결과를 따른다

- 완전 성공: 현재처럼 목록·Action과 필요한 활성 경로 표시를 갱신하고 완료 안내를 표시한다.
- 실패 후 원상 복구: 완료 안내를 표시하지 않는다. 활성 경로와 안내를 유지하고 ID가 바뀌었으면 선택만 다시 연결한다.
- 복구 실패: 실제 남은 데이터를 다시 조회해 패널·Action을 갱신한다. 활성 경로가 없거나 안내 연결이 깨졌다면 해당 표시를 정리하고 부분 실패를 알린다. 실패라는 이유로 모든 현재 표시를 무조건 지우지는 않는다.

현재의 단일 이력 추가, 개별 삭제, 전체 삭제, 파일 가져오기에서 같은 결과 의미를 사용한다. 뷰어로 보내는 신호 계약은 유지하고 성공 신호와 오류 신호를 뒤섞지 않는다.

## 구현 단위

1. 공통 실패 타입·provider 결과 처리·사전 확인을 추가하고 단일 이력 추가와 개별/전체 삭제를 보강한다.
2. 파일 가져오기를 경로·안내 준비 후 저장소의 공통 적용 경로로 연결하고 실패 시 보상 복구를 검증한다.
3. 실패 후 UI 상태와 완료 안내를 수정하고 정상 내보내기·import·조회·삭제·브리지 검증을 다시 수행한다.
4. 별도 변경으로 CRS·geometry·schema·배치 ID 중복·고아 안내 입력 정책을 보강한다. 이번 provider 실패 처리에 모든 입력 정책 변경을 한꺼번에 섞지 않는다.

파일 내보내기의 여러 파일·데이터와 QML·GeoPackage 두 레이어의 부분 저장도 별도 문제다. 이번 재현은 세션 메모리 이력 변경에 대한 것이며 디스크 출력의 원자성까지 검증하지 않았다.

## 수정 완료 검증 기준

- 이번 실제 읽기 전용 provider 조건은 변경 전 실패하고 양쪽 데이터·활성 상태를 유지한다.
- 쓰기 가능한 실제 메모리 레이어에 대한 실패 주입으로 첫 단계 성공/후속 실패, 배치 부분 반영, 예외를 검사한다. 단순 False 반환 mock만 확인하지 않고 실제 남은 feature를 조회한다.
- 추가·삭제 보상 복구 성공 후 geometry·속성·history_id·안내 순서·선택이 기존 상태와 일치한다. 복구 실패도 주입해 실제 잔여 상태와 사용자 오류 안내를 확인한다.
- 오류가 준비한 feature 개수를 성공 건수로 반환하지 않고 UI가 성공 안내를 표시하지 않는다.
- 정상 import의 재불러오기·필드 복원과 활성/비활성 삭제, 내보내기 네 형식, QGIS 3·4 및 동시 외부 연동의 기존 정상 동작을 유지한다.

실패 재현 스크립트는 정상 QGIS 스모크와 같은 방식으로 실행하되 `tests/qgis_history_failure_audit.py`를 지정한다. 결과는 `FAILURE_AUDIT`, `status: reproduced`로 출력된다.
