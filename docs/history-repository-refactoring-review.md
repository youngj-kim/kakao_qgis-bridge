# 이력 저장소 조회·불러오기·삭제 분리 검토

검토일: 2026-10-07. 현재 `history_repository.py`, `plugin.py`, `history_export_service.py`와 런타임 검증 스크립트를 정적으로 확인했다. 앞선 내보내기 분리는 사용자가 QGIS 3·4 정상 작동을 확인했다. 이번 변경은 검토 문서만 작성하며 실행 코드와 테스트 ZIP을 바꾸지 않는다.

## 결론

`HistoryRepository`에 데이터 조회·추가·삭제를 모으는 방향이 적절하다. 다만 원본 파일 읽기와 스키마 대응까지 UI 조정 코드와 함께 이동하면 저장소가 다시 커진다. 저장소, 파일 가져오기, 화면 상태 조정의 경계를 나눈다. 우선 기존 동작을 검증하고 책임을 이동한 뒤, 발견한 실패 처리·입력 검증 문제를 별도 변경으로 보강한다. 저장소 분리만으로 데이터 일관성을 보장했다고 설명하지 않는다.

## 현재 책임과 권장 경계

| 현재 기능 | 권장 담당 | 플러그인에 남길 조정 |
| --- | --- | --- |
| 이력 레이어 생성·append | HistoryRepository | 완료 후 QAction·이력 패널 갱신 |
| `_route_feature_for_history`, `_guidance_features_for_history`, `_memory_history_ids` | HistoryRepository | 활성 이력 ID와 표시 선택 |
| `_open_history_sources`, `_append_imported_history`, 필드 복원 | HistoryImportService | 파일 대화상자와 실패·완료 안내 |
| 전체·개별 이력 feature 삭제 | HistoryRepository | 삭제 확인, 활성 경로 정리, 뷰어·패널·Action 갱신 |
| `_focus_route_history`, `_load_route_history` | 우선 plugin.py 유지 | 지도 이동·경로 레이어 재생성·WebChannel/HTTP 전달 |
| 목록·입력·안내 payload 구성 | 우선 plugin.py 유지 | 현재 뷰어 계약을 보존; 후속 HistoryController에서 검토 |
| `_load_styled_gpx` | 우선 plugin.py 유지 | 프로젝트에 GPX 레이어 추가와 QML 로드; 세션 이력 import와 다른 기능 |

저장소는 조회 결과를 `QgsFeature` 복사본으로 반환하고 안내는 현재처럼 sequence 순서를 유지한다. `iface`, Dock, 브리지 서버, 대화상자를 받지 않는다. 파일 가져오기 서비스는 원본 레이어의 자료를 읽어 저장소에 전달하고, 파일 형식과 필드 대응을 맡는다. `HistoryExportService`를 통해 파일을 다시 쓰거나 플러그인의 private 메서드를 호출하지 않는다.

전체 삭제와 `HistoryRepository.clear()`는 의미가 다르다. 현재 `clear()`는 unload 시 레이어 참조를 해제하는 기능이며 feature 삭제가 아니다. 새 API에서는 `delete_all()`과 참조 해제를 구분하고, unload 호출의 기존 의미를 유지한다.

## 확인된 보강 지점

### 1. provider 실패와 성공 안내

`HistoryRepository.append()`는 경로 `addFeature`만 확인하고 안내 `addFeatures` 반환값은 확인하지 않는다. 안내 추가가 실패해도 True를 반환할 수 있다.

`_append_imported_history()`는 임시·대상 provider의 `addFeatures` 반환값을 확인하지 않고 준비한 feature 수를 반환한다. 반환 건수는 실제 추가 성공 건수라고 보장되지 않는다. `_load_route_history_file()`은 경로와 안내를 차례로 추가하므로 후속 단계 실패 시 앞선 추가가 남을 수 있다.

삭제 함수도 경로·안내 `deleteFeatures` 성공 여부를 확인하지 않고 활성 표시 정리와 완료 안내를 수행한다. 단순 위임으로 옮길 경우 이 문제도 그대로 남는다.

권장: 구조 이동 후 별도 안정성 변경에서 준비·검증·적용 단계를 구분하고 실패 결과를 호출자에게 전달한다. 두 메모리 레이어는 하나의 DB 트랜잭션으로 자동 묶이지 않으므로 실제 롤백·보상 정책을 구현하고 검증하기 전에는 원자적이라고 표현하지 않는다. 성공한 부분과 실패한 부분을 명확히 반환하며, rollback도 실패할 수 있음을 처리한다.

### 2. 불러오는 CRS와 geometry

`_append_imported_history()`는 대상 임시 레이어를 EPSG:4326으로 만들지만 원본 geometry를 좌표 변환 없이 복사한다. 플러그인의 정상 내보내기 파일은 4326 기준이지만 외부에서 다른 CRS로 변경한 파일은 잘못된 좌표로 들어갈 수 있다. 단순 CRS 라벨 변경은 좌표 변환이 아니다.

권장: 첫 구조 이동에서는 정상 내보내기 파일의 현재 동작을 유지한다. 후속 검증 변경에서 다른 CRS를 명시적으로 거부할지 지원할지 정한다. 변환을 지원하면 geometry뿐 아니라 origin/destination/longitude/latitude·경유지 JSON의 좌표 의미도 함께 다뤄야 한다. 확인되지 않은 외부 파일을 geometry만 변환해서 안전하다고 처리하지 않는다. geometry 종류·비어 있는 geometry·좌표 범위도 입력 계약에 포함한다.

### 3. 중복과 경로·안내 연결

불러오기 시작 시 대상의 history_id 집합만 구한다. 파일 내부에서 같은 history_id의 경로 feature가 반복되면 이번 배치에서 추가할 ID는 집합에 반영되지 않으므로 여러 경로를 추가할 수 있다. 안내는 한 이력에 여러 feature가 필요하므로 같은 history_id가 정상이다. 경로와 안내에 같은 중복 규칙을 적용하면 안내를 잃는다.

또한 두 레이어를 독립적으로 import하므로 연결된 경로가 없는 안내를 거르는 명시적인 검증은 없다. 같은 history_id의 기존 경로와 파일 경로가 다른 경우도 단순히 대상 ID를 기준으로 건너뛴다.

권장: 후속 변경에서 경로의 배치 내 ID 중복, 안내의 sequence·연결된 경로, 기존 동일 ID 충돌을 각각 구분한다. 기존 이력에 안내가 전혀 없는 경우 현재 코드가 안내를 보충할 수 있다는 동작도 기록한다. 불완전 안내의 복구·덮어쓰기는 별도의 정책으로 정한다.

### 4. 스키마 대응

현재 전체 필드명과 SHP 짧은 필드명의 매핑이 내보내기와 불러오기에 각각 있다. `_history_value()`는 전체 이름이 있으면 우선하며, 어느 이름도 없으면 None을 넣는다. schema_ver 필드는 있지만 명시적인 지원 버전 판정이나 필수 필드 검증은 없다.

권장: 공통 `history_schema.py`에 필드 이름 대응을 모으되 레거시 파일의 기존 복원 결과를 먼저 고정한다. SHP 문자열 제한 등 writer 전용 옵션은 내보내기 서비스에 둔다. 필수·선택 필드, 레거시 기본값, 지원하지 않는 미래 버전의 거부 정책은 안정성 변경에서 추가한다. 지원 가능한 필드 일부만 가져온 것을 완전 복원이라고 안내하지 않는다.

## 권장 진행 순서

1. **기존 기준 검증:** 이력 조회·안내 정렬, GPKG/GeoJSON/SHP import, 재import 중복 방지, 전체/짧은 필드명 복원, 없는 ID, 삭제 취소·개별·전체 삭제를 QGIS 3·4에서 확인한다. GPX는 프로젝트 레이어 불러오기로 별도 확인한다.
2. **책임 이동:** 조회와 feature 삭제는 저장소로, 파일 소스 열기와 import는 서비스로 분리한다. UI 동작·payload·파일 계약은 유지한다. 공유 필드 매핑도 이 단계에서 중복을 줄일 수 있다.
3. **일관성 보강:** provider 실패, 부분 적용, CRS·geometry·schema 검증, 배치 중복과 고아 안내를 별도 변경으로 처리한다. 기존의 정상 파일 출력·복원은 유지한다.
4. **패키지 및 사용자 확인:** 기존 내보내기 테스트, 플러그인·브리지 회귀 검증을 수행한 뒤 새 테스트 ZIP을 만든다. QGIS 3·4에서 삭제 후 활성 경로와 이력 패널 상태, 다시 불러오기, 동시 외부 연동을 확인한다.

## 완료 기준과 범위

- 조회 결과를 바꿔도 저장소 원본이 바뀌지 않고, 없는 ID는 기존처럼 빈 결과를 반환한다.
- 정상 파일을 처음 가져온 건수와 다시 가져온 건수, 필드·geometry·안내 순서가 기존 기준과 일치한다.
- 개별 삭제는 해당 경로와 안내만 제거한다. 비활성 이력을 지워도 활성 경로를 유지하고, 활성 이력 삭제 시 표시·안내 상태를 함께 정리한다.
- 전체 삭제 시 Action과 패널·뷰어 상태를 갱신하고, 확인을 취소하면 데이터와 표시를 유지한다.
- 실패 주입으로 실제 provider 실패를 확인하며 완료 안내·반환 건수·부분 데이터가 정한 정책과 일치해야 한다. mock한 성공만으로 일관성 보강 완료를 판정하지 않는다.
- 저장소와 서비스는 QGIS 프로젝트·뷰어의 전체 수명을 맡지 않는다. 레이어 수동 삭제나 프로젝트 교체에 대한 LayerManager 설계, 자동 영속화, 19개 append 인자를 모델로 묶는 변경은 후속 범위다.

이번 검토는 정적 검토다. 위의 잘못된 파일·provider 실패를 QGIS에서 재현한 결과는 아직 아니며, 정상 import·삭제의 기준 검증부터 다음 구현 단계에서 진행한다.
