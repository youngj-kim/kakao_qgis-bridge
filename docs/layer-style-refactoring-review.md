# 레이어 관리·스타일 책임 분리 검토

검토일: 2026-10-07. 기존 저장 파일 호환성 수정은 사용자 정상 확인을 받았다. 다음은 최초 리팩터링 계획의 남은 표시 레이어/스타일 경계다. 이번 단계는 정적 검토이며 실행 코드와 ZIP을 변경하지 않는다.

## 결론과 변경 순서

먼저 `StyleFactory`로 심볼/renderer 생성만 옮긴다. 이후 `DisplayLayerManager`로 현재 경로·안내·출발/도착/경유지 핀·로드뷰 표시 레이어를 옮긴다. 두 변경을 한 번에 기능 확장과 묶지 않는다. 줌 동기화, 자동 저장, 인증 관리자와 전송 방식 변경은 이후 독립 범위다.

| 대상 | 맡길 책임 | 남길 책임 |
| --- | --- | --- |
| StyleFactory | 경로 선, 안내/GPX 분류, 핀, 로드뷰 radar, SVG 인코딩 및 Qt 버전 호환 | UI 메시지, 프로젝트 접근, 이력 데이터 |
| DisplayLayerManager | 표시 레이어 생성·갱신·제거, feature ID 참조, 안내 선택, 실제 점만 범례에 표시, 사용자 category 캐시 | 지도 범위/캔버스 이동, 활성 이력, 웹 payload, REST 요청 |
| HistoryRepository | 내부 이력 레이어 및 checked 변경/복구 | 표시 레이어 관리와 프로젝트 지도 레이어 등록 |
| plugin.py | 서비스 조립, UI, 동기화, 요청/결과 조정, 범위 맞춤 및 알림 | 서비스가 plugin 전체를 받아 private 메서드를 호출하는 구조는 만들지 않음 |

현재 이력 레이어는 저장소 내부 메모리이고 표시 레이어는 프로젝트에 등록된다. 이를 이름이나 geometry 종류로 합치면 삭제/수명이 달라져 데이터 손실 위험이 있다. 스타일 팩토리는 두 곳과 export 서비스에서 공유하되 매 호출마다 새 심볼/renderer를 반환한다. QGIS 소유권 이전 객체를 재사용하지 않는다.

## 현재 확인한 구조와 보존 계약

- `plugin.py`의 `_route_line_symbol`, `_route_guidance_renderer`, `_gpx_waypoint_renderer`, `_guidance_symbol`, `_route_pin_symbol`, `_embedded_svg_path`를 우선 옮길 수 있다. 로드뷰 radar 생성도 팩토리 대상이다.
- 안내 renderer는 `category`, GPX renderer는 `type`으로 분류한다. 같은 아이콘이어도 분류 값·라벨이 다르므로 무리하게 하나로 합치지 않는다. 핀 크기 9/7.5, 안내 크기 6.5, bottom anchor, 선 색/두께, radar pan 회전과 SVG base64 경로를 보존한다.
- export 서비스는 현재 심볼 factory 콜백을 받아 새 객체를 만든다. 이 주입 계약을 유지하며 plugin 클래스에 SVG/Qt 처리가 다시 의존하지 않게 한다. SVG 내용 인코딩 문자열 캐시는 가능하지만 QGIS 심볼 객체 캐시는 피한다.
- 핀 범례는 실제 feature role만 나타내며 역할이 다시 생기면 사용자 심볼·라벨·체크 상태를 복원한다. 사용자 정의 non-role renderer는 그대로 둔다. 첫 레이어 생성·삭제 시 cache 초기화도 관리자의 책임이다.
- 현재 경로/안내는 다시 만들 때 이전 표시 레이어를 제거한다. 로드뷰/핀은 기존 유효 feature를 갱신한다. 첫 책임 이동은 이 동작, 필드 순서·자료형·정밀도·이름·skipMemoryLayersCheck·선택·프로젝트 등록 수를 보존한다.
- 지도 범위 맞춤은 plugin/컨트롤러에서 처리한다. 관리자는 iface나 canvas를 받지 않고, 생성한 레이어/geometry 또는 결과를 반환한다.
- 플러그인의 기존 private 메서드/레이어 속성은 필요하면 얇은 위임으로 남겨 기존 테스트 및 호출부를 단계적으로 유지한다. 관리자가 plugin 객체를 받는 역방향 위임은 하지 않는다.

## 수명과 실패 처리에서 추가 확인할 사항

현재 ensure/remove/focus 일부는 삭제된 C++ 레이어 접근의 RuntimeError를 처리하지만 프로젝트 레이어 제거/프로젝트 초기화 신호를 통한 참조 정리는 없다. 수동 삭제 후 ensure 재생성 경로가 있는 로드뷰·핀과, 안내 feature ID·활성 이력·웹 표시 상태는 책임이 다르다. 즉시 삭제와 다음 조작 시 재생성, 프로젝트 전환, 종료를 실제 QGIS에서 별도로 재현해야 한다. 이번 정적 검토만으로 사용자 오류가 발생한다고 단정하지 않는다.

표시 레이어 삭제만으로 내부 이력을 삭제하거나 복구 차단 상태를 초기화하지 않는다. 레이어 소유권은 이름 대신 manager가 보관한 ID/참조로 판정한다. 사용자가 추가한 일반 레이어와 GPX 불러오기 레이어는 manager의 일괄 제거 대상이 아니다. unload에서는 신호/타이머 연결을 해제하고 manager 소유 표시 레이어만 제거하며 이력 clear의 기존 계약을 유지한다.

프로젝트 전환 시 내부 이력을 자동 삭제할지는 현재 범위에서 바꾸지 않는다. 활성 표시/웹 상태 및 진행 중 REST 응답을 새 프로젝트에서 어떻게 처리할지는 재현과 상태 정책을 별도 검토한 후 변경한다. 단순 class 분리에 이력 폐기 정책을 끼워 넣지 않는다.

현재 표시 경로 addFeature와 일부 changeGeometryValues/changeAttributeValues/deleteFeatures는 반환값을 확인하지 않는다. 이력 변경의 보상 복구와 성격이 다르므로 같은 engine을 무리하게 공유하지 않는다. 먼저 실제 실패 재현과 알림/기존 표시 보존 정책을 정하고 별도 안정성 변경에서 처리한다. 현재 요청 성공·이력 저장 실패의 표시 유지 정책을 깨뜨리지 않는다.

## 구현·검증 순서

1. 심볼/renderer의 현행 기준을 QGIS 3·4에서 확보한다: 분류 키·category 값/라벨·심볼 크기·anchor·SVG 경로·선 속성·radar 회전. fresh 객체가 서로 영향을 주지 않는지도 검사한다.
2. StyleFactory를 분리하고 기존 GPX/GPKG/GeoJSON/SHP 스타일 재불러오기 및 범례 검증을 실행한다. 저장 스키마와 파일 writer는 바꾸지 않는다.
3. 표시 레이어 관리의 생성·갱신·선택·삭제 기준을 확보한 뒤 manager로 이동한다. 지도 범위와 활성 이력/UI 갱신은 기존 조정 코드에 남긴다.
4. 실제 QGIS에서 수동 레이어/feature 삭제와 재생성, 반복 생성/제거, 프로젝트 초기화, unload, 다른 일반 레이어 보존을 검사한다. pending 요청/웹 상태 정책과 provider 실패는 별도 보강 범위로 구분한다.
5. 기존 입력 검증·이력 실패 복구·내보내기·범례/브리지 테스트를 회귀 실행한다. 변경된 책임과 관련된 검증을 우선하며 사용자에게 같은 파일 검사를 반복 요구하지 않는다.

이번 검토의 다음 구현 단위는 **스타일 팩토리 분리**다. 다음 단계 ZIP은 해당 단위가 자동 검증을 통과한 뒤 생성한다. 현재 사용 중인 import-compatibility ZIP은 그대로 유지한다.
